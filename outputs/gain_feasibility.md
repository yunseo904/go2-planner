# Can the joint gains be changed at runtime?

Generated by `scripts/report_gain_feasibility.py`. Numbers are read from the
upstream source (`extreme-parkour/legged_gym/legged_gym/envs/base/legged_robot_config.py`), the clip archive and the curated logs at generation time.

**Short answer: yes, and the repo already does it.** The Go2 actuators in this fork are
*explicit* — the PD runs in Python during `write_data_to_sim()` and reads
`actuator.stiffness` at that moment — so assigning new gains takes effect on the next
step with no PhysX call. `_apply_domain_randomization()` uses exactly this mechanism
today, per-env and per-joint. The open question is not *whether* but *how often*, and
the answer to that is: less often than expected, because the log's gain schedule is
near-constant within a skill.

There is a second, larger problem that this investigation turned up and that gain
scheduling does **not** solve — see [Torque headroom](#torque-headroom).

## What was read from the source

These are facts, checked on this machine with no Isaac Lab installed.

| fact | value | where |
|---|---|---|
| Isaac Lab | `isaaclab 6.1.14` / `isaacsim 6.0.0.1` (Isaac Lab 3.0), Python 3.12 | `environment_eureka_lab6.yml`, `pip_freeze_eureka_lab6.txt` |
| sim step | `dt = 0.005` s | `extreme-parkour/legged_gym/legged_gym/envs/base/legged_robot_config.py` |
| decimation | `4` | same |
| **control rate** | **50 Hz** | derived; matches the clips' `lo` rate exactly |
| action scale | `0.25` | position target = `action_scale x action + default_joint_pos` |
| actuator `hip_thigh` | `IdealPDActuatorCfg` kp=40.0 kd=1.0 effort=23.7 Nm vel=30.1 rad/s | same |
| actuator `calf` | `IdealPDActuatorCfg` kp=40.0 kd=1.0 effort=45.43 Nm vel=15.7 rad/s | same |
| actuators explicit? | **True** | `IdealPDActuator` computes torque in Python, not PhysX |
| runtime gain change | **already in use** | `LeggedRobot._apply_domain_randomization()`: `act.stiffness *= motor_strength[0][:, ids]`, per-env per-joint tensors |
| gain DR range | `motor_strength_range = [0.8, 1.2]`, `randomize_motor = True` | `legged_robot_config.py` |
| effort target used? | **no** — only `set_joint_position_target` | `LeggedRobot._apply_action()` |

The important one is the actuator class. The fork *deliberately* moved off `DCMotorCfg`
to `IdealPDActuatorCfg` ("DCMotor's torque-speed derating is an extra constraint the
original never had, and it drove the policy into a crawling local optimum") — which means
the PD is Python-side by design, and Python-side is precisely what makes gains schedulable.

**The stock Isaac Lab Go2 gains (kp 25 / kd 0.5) are not what this project uses.** An
earlier note in `outputs/skill_clips.md` compared against those; it is corrected here. The
fork uses kp 40 / kd 1, which is *exactly* what the
position-controlled log sessions commanded. WALK and TROT need no gain change at all.

## What still has to be probed

Isaac Lab is not installed here, so these are asserted from the API and must be checked
before they are relied on. `scripts/probe_isaac_actuator.py` checks all of them in about
a minute and writes `isaac_actuator_probe.json`; it measures `robot.data.applied_torque`
rather than testing whether a method exists.

| # | assertion | how the probe decides |
|---|---|---|
| 1 | the actuators are explicit at runtime, not just by class name | doubles `stiffness`, expects the applied torque magnitude to double |
| 2 | assigning `actuator.stiffness` (not just `*=`) is honoured | same test |
| 3 | `set_joint_effort_target` **adds** to the PD term rather than replacing it | commands +5 Nm, expects `applied_torque` to shift by +5 |
| 4 | `write_joint_stiffness_to_sim` exists and is the *implicit* path, irrelevant here | calls it, records accept/raise |
| 5 | torque is clipped at `effort_limit` with no torque-speed curve | commands an absurd position error, reads the plateau |

If (3) comes back "replaces" or "ignored", every feed-forward mode is out and the fallback
chain below drops straight to `position`.

## Do the gains actually need to change every step?

| clip | log kp (hip/thigh/calf) | log kd | sim kp/kd | tau_ff RMS (Nm) | position-controlled? |
|---|---|---|---|---|---|
| `WALK` | 40 / 40 / 40 | 1 / 1 / 1 | 40 / 1 | 0 / 0 / 0 | yes |
| `TROT` | 40 / 40 / 40 | 1 / 1 / 1 | 40 / 1 | 0 / 0 / 0 | yes |
| `RUN` | 13 / 3 / 2 | 1.8 / 2 / 1.5 | 40 / 1 | 3.67 / 2.59 / 11.79 | **no** |
| `JUMP` | 40 / 40 / 40 | 1.8 / 2 / 1.5 | 40 / 1 | 2.91 / 4.17 / 12.23 | yes |

Two clips need nothing: WALK and TROT were recorded at the config's own gains with zero
feed-forward. Two need the real treatment: RUN sits at kp 13/3/2 — a calf gain of 2 Nm/rad
is a nearly free leg — and JUMP carries ~10-14 Nm RMS of feed-forward.

Within a skill the gains are *piecewise constant*, not continuously varying: the sport
controller switches between a handful of discrete levels. That is why option (a) below
costs so little.

## The four replay modes

Implemented in `sim/replay.py`, selected with `verify_skill_replay.py --mode`. A requested
mode is resolved against what the installed Isaac Lab supports and the **resolved** mode is
recorded with the result, so a run can never be reported under a mode it did not use.

| mode | gains | tau_ff | needs | loses |
|---|---|---|---|---|
| `torque` | per step, from the clip | per step | runtime gain write + effort target | nothing |
| `fixed-gain` **(a)** | one pair per skill, set before sim start | per step | effort target only | the within-skill gain schedule |
| `ff-only` **(b)** | config kp 40 / kd 1 | per step | effort target only | the whole gain schedule |
| `position` | config kp 40 / kd 1 | none | nothing | everything torque-driven |

Fallback chain: `torque` → `fixed-gain` → `ff-only` → `position`.

### (a) per-skill fixed gains — the recommended fallback

Set the actuator gains on the `ArticulationCfg` before the sim starts, one pair per skill,
and re-set them on a skill switch. Cheap, needs no runtime API, and because the log's gains
are piecewise constant per skill it loses very little. The cost: a skill switch now has a
gain discontinuity, which the real robot also had, so this is arguably more faithful than
interpolating.

For the planner this is a *good* fit — it already models skills as discrete with a switch
delay, so "switch the gains with the skill" falls out of the existing state machine rather
than being bolted on.

### (b) feed-forward torque path

`Articulation.set_joint_effort_target()` feeds `control_action.joint_efforts`, which
`IdealPDActuator.compute()` adds to `kp*e_pos + kd*e_vel` before clipping. Position target
and effort target can be set on the same step. **Asserted, probe item 3.** The fork never
uses it, so nothing in-repo confirms it.

### (c) parameter-based gait generator — the real fallback

If neither gains nor feed-forward can be applied, clip replay cannot reproduce RUN and
there is no point pretending otherwise. Drop to a parameterised gait: contact schedule
(period, duty, phase offsets) plus a swing trajectory, with the parameters taken from
`outputs/skill_profile.csv` rather than invented.

The repo already leans this way — `scripts/record_gait.py` records "a 4xT 0/1 step pattern
(the WHEN)" from a trained policy "to ground the saytap step-pattern library in a real
controller". A gait generator driven by the *measured* contact schedule is the same idea
with the curated logs as the source instead of a policy. The clips already carry the
contact signal, so the WHEN is in hand; only the WHERE would need building.

This costs the most and buys the most robustness: it has no convention problem, no gain
problem and no torque problem, because it never replays a recorded trajectory.

## Torque headroom

This is the finding that gain scheduling does not fix.

`IdealPDActuator` clips torque at a static `effort_limit`. The real robot went past it.

| clip | joint | peak logged (Nm) | p99.9 | sim limit | peak/limit |
|---|---|---|---|---|---|
| `WALK` | hip | 8.16 | 7.92 | 23.70 | 0.34×  |
| `WALK` | thigh | 9.82 | 8.14 | 23.70 | 0.41×  |
| `WALK` | calf | 16.55 | 16.37 | 45.43 | 0.36×  |
| `TROT` | hip | 6.58 | 6.44 | 23.70 | 0.28×  |
| `TROT` | thigh | 18.75 | 18.17 | 23.70 | 0.79×  |
| `TROT` | calf | 24.37 | 24.23 | 45.43 | 0.54×  |
| `RUN` | hip | 15.12 | 11.12 | 23.70 | 0.64×  |
| `RUN` | thigh | 27.53 | 26.18 | 23.70 | 1.16× **OVER** |
| `RUN` | calf | 42.06 | 38.58 | 45.43 | 0.93×  |
| `JUMP` | hip | 19.17 | 18.05 | 23.70 | 0.81×  |
| `JUMP` | thigh | 26.15 | 25.69 | 23.70 | 1.10× **OVER** |
| `JUMP` | calf | 54.67 | 50.18 | 45.43 | 1.20× **OVER** |

RUN's thigh and JUMP's thigh and calf exceed the configured clip by 10-20%. The logged
`tau` is the firmware's estimate (`tau_est`), not a load-cell reading, so treat the
magnitude as approximate — but the direction is not in doubt, and the hip/thigh limit
of 23.7 Nm is annotated in the source as coming from a spec sheet.

Consequence: **the sim robot is weaker than the one that produced these clips.** A jump
replay will fall short of 0.25 m, and `STEP_JUMP_MAX` measured on the probes will be a
property of the sim robot.

That is the *correct* thing to calibrate — the planner is evaluated in sim, so a limit
that describes the sim robot is the limit the planner needs. What must not happen is
raising `effort_limit` for the calibration run only: that would calibrate against a
robot the evaluation never instantiates, and it is exactly the kind of per-arm tweak
`CLAUDE.md` §2 rules out. Record the gap; do not close it.

Check it directly with `verify_skill_replay.py --headroom`, and watch
`torque_saturated_frac` in the replay results.

## Recommendation

1. Run `scripts/probe_isaac_actuator.py` first. Everything below branches on it.
2. Verify WALK and TROT in `position` mode. Their gains already match the config, so a
   failure there is a convention bug, not a gain bug — a clean separation of concerns.
3. Verify RUN in `torque` mode, falling back to `fixed-gain`. Expect it to fall short on
   forward speed regardless, because of the thigh torque clip.
4. Treat JUMP as the least trustworthy replay: it is over the clip on two joint groups.
5. Keep (c) costed. If probe item 3 fails, it is not a fallback, it is the plan.

## Correction applied elsewhere

`outputs/skill_clips.md` and `motion_toolkit/README.md` previously compared the log's gains
against Isaac Lab's *stock* Go2 defaults (kp 25 / kd 0.5). That is a different robot from
the one this project instantiates. Both now quote the fork's kp 40 / kd 1.

The conclusion did not change — RUN was recorded at kp 13/3/2, and 40 is further from
that than 25 was, so a position replay of RUN is *more* wrong than first stated. But one
consequence did change, in the useful direction: **WALK and TROT need no gain handling at
all**, because kp 40 / kd 1 with zero feed-forward is exactly what they were recorded at.
